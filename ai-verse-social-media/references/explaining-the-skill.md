# Explain the skill so people can use it

Read this for newcomer introductions, feature questions, help getting started and feature discovery. [START-HERE.md](../START-HERE.md) is the customer capability map. Adapt it; do not recite it as a script.

## Help them understand and act

Explain the useful outcome first: their AI assistant helps prepare and post videos, then remembers what happened. “Prepare → Choose → Publish → Remember” is an optional memory aid. Use their situation and vocabulary. Simple language should be respectful, not childish, whatever the person's age or experience.

For each feature you explain, make clear **when it helps, what they provide, what the assistant does and what they receive**. A short example often does more than a technical definition. The person should know what they can ask next.

## Reveal detail when useful

- **First introduction:** short purpose sentence, a small numbered overview and one easy starting action. Do not unload every feature.
- **“Everything it does”:** complete, short numbered feature map; link the guide for revisiting. Keep examples and limits beside the relevant feature.
- **Specific need:** explain the feature that solves it. Introduce related options only if they help the person's decision.
- **Setup:** explain this step and its purpose, then ask for the missing choice. A missing connection needs a next action, not a wall of diagnostics.
- **After an action:** give the actual outcome. Occasionally mention one useful next feature when the situation makes it relevant; do not attach a tutorial to every reply.

These are judgment guides, not fixed templates or sentence counts. Change wording, order, length and examples naturally. Examples never become required activation phrases. Requests in ordinary language retain the same capability and approval rules.

## Make it easy to read

Prefer short sentences, familiar words, numbered chunks and space between ideas. Put the benefit or action first. Define unfamiliar terms only when needed: caption = text beside the video; draft = saved for review; posting history = a checklist of what went out where.

Translate machinery into outcomes. “Backfill” becomes using eligible older videos on a newly included account. Leave internal IDs, schemas and worker details for technical help. Use the customer's actual accounts and content when known; do not assume a school, business, specific platform or unattended routine.

## Explain accurately

Use the customer guide and [feature matrix](../FEATURE-MATRIX.md) as the capability boundary. Route actual work to the existing operational references. This document changes communication, not authorization or execution.

If the workspace is known, check its saved settings/status before claiming that connections or routines are ready. Otherwise describe what is possible after setup. Local tests do not prove live account or host support.

Keep these distinctions clear when relevant:

- An upload or explanation request does not authorize posting. “All” means the customer's included accounts with verified support, not every platform.
- A one-account request does not authorize wider distribution. The reusable collection contains videos the customer allows for regular posting and future included accounts.
- Draft, scheduled and published are different results. Show actual account outcomes, times and links when known. Partial success is not “everything done.”
- Time suggestions use available history and allowed times. Little history means a suitable allowed time, not a guaranteed winner.
- Caption memory uses saved examples and feedback; it does not retrain the model. Editing supports the guide's specific changes, using actual speech text and supplied branding assets.
- Regular posting needs approved rules and the host's scheduler. Installing the skill alone does not create an always-running employee.
- Pause does not cancel remote schedules. Cancellation cannot undo a published post or guarantee stopping one already being sent.
- For comments or DMs, explain that onboarding can gather reply rules and check an available engagement integration. A questionnaire or Zernio connection alone does not enable replies; the local video engine has no engagement worker. Route to [engagement setup](engagement-setup.md).
- Recovery checks existing attempts before sending again. Folder problems or failed accounts must not cause successful accounts to be reposted.
- Filing depends on the accounts required for that video's distribution; a one-time request and a reusable video may have different completion requirements.

Before sending, check whether a newcomer could answer: **What will this help me do? When would I use it? What can I ask next?** Simplify if not. Correct any wording that makes an unconnected or untested feature sound ready.
