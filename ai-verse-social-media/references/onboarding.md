# Guided onboarding and setup audit

For a newcomer, first explain the useful outcome and current step in ordinary language; use [the explanation guide](explaining-the-skill.md) and [customer feature guide](../START-HERE.md) as needed. Introduce features as they become useful instead of asking the person to learn the whole system before starting.

1. Resolve a new or existing private customer workspace. Run `init` once; it preserves existing settings. Run `audit`; show Ready / Needs setup / Optional and one next step.
2. Ask which modes the customer wants: live posting, recurring library workflow, editing, optional intake/engagement. Offer comment replies, incoming DMs and comment-to-DM setup as separate choices. If requested, follow [engagement setup](engagement-setup.md), asking relevant questions in small batches and saving progress; verify an available Zernio/host route before enabling it. Enable ready core paths without requiring every optional feature.
3. Use [empty examples](../examples/README.md) when useful; never reset an existing workspace. Guide Zernio connection using the host's secret store. `profiles` lists identities; confirm the actual customer's profile(s), put their IDs in `settings.json`, then `accounts --sync`. Do not guess IDs or select all profiles by default.
4. Confirm intended accounts and whether future accounts inside this profile should enroll automatically. `account-policy` selects/enables destinations and stores verified capability contracts. Verify `health` and current official platform docs; required fields/limits and evidence belong in capability settings. TikTok privacy/consent is creator-specific and must be configured from the current account options. YouTube can derive its title from the first caption line. Provider discovery alone is not proof that every platform accepts video.
5. Connect Drive if requested. Reuse or guide the customer to create their folders in Drive; the engine does not silently create a remote folder tree. Map folder IDs for `incoming`, `processing`, `ready`, `posted`, `review`, and `originals`. For request-only publishing, also map a clearly labeled `request_scoped` subfolder under Posted; this keeps one-platform results distinct from the recurring library. Ask whether chat/local videos may be copied into Drive after every requested destination verifies; Drive connection alone does not authorize this copy. Reuse existing folders. Any new folders/moves require the user's scope approval; `audit --live` verifies read-only access. Scope OAuth to required features.
6. Ask caption preference: reusable idea adapted to each video/platform, customer wording each time, transcript-based recommendation, or hybrid. Ask for an example and useful preferences: language, voice, CTA, links, hashtags/emojis, length, words to avoid, exact wording versus free adaptation. Record customer responses in the caption journal and settings. Do not force a lengthy questionnaire when their examples suffice.
7. Ask editing defaults, supplied brand assets, preview preference, and whether live submissions should join recurring distribution. Explain that 'only Instagram' does not authorize other accounts, and future-account archive backfill follows library enrollment restrictions.
8. Configure IANA timezone, approved windows, spacing/daily limits, missed-slot behavior, and standing authorization. Recurring scheduling cannot be enabled without recorded recurring scope. Create scheduler integration only after readiness/tests. Schedule bounded intake, agent preparation, and provider tick steps separately; verify saved timezone/scope and next run; an engine config flag does not activate it.
9. Run a synthetic local workflow and provider draft/private test where supported. Explain what is and is not tested. Public tests require explicit authorization. `audit --live` checks connected account identities and batch publishing health through Zernio, and checks Drive without refreshing expired credentials. Show final readiness and save remaining steps in `onboarding-audit.json`.

Rerun resumes and verifies; it doesn't erase preferences, resync private sources from scratch, or create duplicate folders/schedules. Limit audit to known paths and configured accounts/folders, with a 120-second target budget. Save partial results if external checks take longer. Never spend hours classifying the whole host as part of onboarding.

Optional engagement has its own private `engagement-setup.json` decisions, integration evidence and test status. Review that record alongside the video audit. An engagement questionnaire or an existing Zernio connection does not itself mean automatic replies are running.

Offer an optional [silent weekly update check](updates.md). With the customer’s authorization, configure exactly one host-native job, verify worker GitHub access, test conditional silence and confirmed delivery/acknowledgement, and read back its next run. Save progress if scheduler/authentication is missing. Notify only on a newly detected revision or a new blocker; do not auto-install updates.
